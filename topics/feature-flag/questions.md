## 기초

### Q. 피처 플래그(Feature Flag)란 무엇이고, 왜 사용하나?

**핵심 키워드**: Deployment와 Release 분리, 런타임 제어, 롤백

**모범 답변 방향**:  
피처 플래그는 코드 배포 없이 특정 기능을 런타임에 켜고 끌 수 있는 설정값이다. 핵심 가치는 **Deployment(코드 배포)와 Release(사용자에게 기능 공개)를 분리**하는 것이다.

예를 들어 새로운 결제 흐름을 개발했을 때, 코드는 이미 main 브랜치에 배포되어 있지만 플래그가 false이면 사용자는 기존 흐름을 본다. 준비가 됐을 때 플래그를 true로 바꾸는 순간 재배포 없이 기능이 오픈된다.

주요 사용 목적은 세 가지다:
1. **점진적 롤아웃**: 1% → 10% → 100% 단계적 확대, 이상 발생 시 즉시 0%로 롤백
2. **킬 스위치**: 장애 시 재배포 없이 수초 내 기능 비활성화
3. **A/B 테스트**: 사용자 그룹별로 다른 경험 제공 후 데이터로 의사결정

---

### Q. 피처 플래그의 종류(유형)를 설명하라.

**핵심 키워드**: Release Flag, Experiment Flag, Ops Flag, Permission Flag, 수명 차이

**모범 답변 방향**:  
Martin Fowler의 분류 기준으로 4가지 유형이 있으며, **수명**과 **동적성**에서 차이가 난다.

**Release Flag**: 가장 흔한 유형. 미완성 기능을 main 브랜치에 머지하되 플래그로 숨겨두는 용도. 100% 롤아웃 후 제거해야 하므로 **단기** 수명.

**Experiment Flag**: A/B 테스트용. Boolean이 아닌 Variant(blue/green/red)를 반환. 실험 종료 후 승자가 결정되면 제거하는 **단기** 수명.

**Ops Flag(Kill Switch)**: 장애 시 즉시 기능을 끄는 비상 차단기. 기능이 살아있는 한 유지하는 **장기** 수명. 변경이 즉시 반영되어야 하므로 캐시 TTL을 최소화.

**Permission Flag**: 요금제, 역할, 지역에 따라 기능 접근을 제어. 비즈니스 로직의 일부이므로 **영구** 수명. 예: Pro 플랜 사용자에게만 고급 분석 기능 제공.

---

### Q. 카나리 배포와 피처 플래그의 차이는?

**핵심 키워드**: 제어 단위(인스턴스 vs 사용자), 롤백 속도, 특정 유저 타겟

**모범 답변 방향**:  
카나리 배포는 **서버 인스턴스 단위**로 트래픽을 라우팅하고, 피처 플래그는 **사용자/요청 단위**로 기능을 제어한다.

| 구분 | 카나리 배포 | 피처 플래그 |
|------|-------------|-------------|
| 제어 단위 | 서버 인스턴스 | 사용자/요청 |
| 롤백 속도 | 트래픽 라우팅 변경 (분 단위) | 플래그 OFF (초 단위) |
| 특정 유저 타겟 | 불가 | 가능 |
| 인프라 | 복수 인스턴스 필요 | 단일 인스턴스 가능 |

실무에서는 두 가지를 함께 사용한다. 카나리로 인스턴스 레벨 안정성을 먼저 확인하고, 피처 플래그로 사용자 단위 점진적 오픈을 한다.

## 심화

### Q. 분산 환경에서 피처 플래그의 캐시 일관성 문제를 어떻게 해결하나?

**핵심 키워드**: 캐시 TTL, Pub/Sub 무효화, 스티키 할당, fail-closed

**모범 답변 방향**:  
여러 인스턴스가 각자 로컬 캐시를 들고 있을 때, 플래그를 변경해도 각 인스턴스의 캐시 TTL이 만료되기 전까지는 반영되지 않는다. 같은 사용자의 요청이 서로 다른 인스턴스에 가면 서로 다른 경험을 받을 수 있다.

해결 방법은 플래그 유형에 따라 다르다.

**Ops 플래그(즉시 반영 필요)**: Redis Pub/Sub으로 플래그 변경 이벤트를 발행하면 모든 인스턴스가 구독해 해당 키의 캐시를 즉시 삭제한다. TTL을 0~10초로 짧게 설정하는 방법도 있다.

**Release/Experiment 플래그(약간의 지연 허용)**: TTL을 30초~5분으로 설정하고 허용. 완전한 일관성보다 성능이 더 중요한 경우.

**사용자 스티키 할당**: `hash(userID + flagName) % 100` 으로 같은 사용자는 어느 인스턴스에 가도 같은 결과를 받도록 보장. 캐시 일관성과는 별개로 반드시 보장해야 한다.

플래그 서비스 자체가 다운될 때는 **fail-closed** (기본값 false 반환)를 원칙으로 한다. 불확실한 상태에서 기능을 활성화하는 것이 더 위험하기 때문이다.

### Q. 피처 플래그 부채(Flag Debt)란 무엇이고 어떻게 관리하나?

**핵심 키워드**: 기술 부채, 만료일, 제거 티켓, 2^n 조합 폭발

**모범 답변 방향**:  
플래그를 추가하고 제거하지 않으면 코드에 플래그가 쌓여 기술 부채가 된다. n개의 플래그가 있으면 이론상 2^n개의 조합이 존재해 코드 복잡도가 폭발한다. 실제 사례로 2012년 나이트 캐피탈 그룹이 구형 플래그 코드의 실수로 45분 만에 4.6억 달러를 잃었다.

관리 방법:
1. **생성 시 만료일 설정**: Release 플래그는 2~4주, Experiment 플래그는 실험 기간
2. **제거 티켓 동시 생성**: 플래그를 만들 때 JIRA/Linear에 제거 작업도 함께 등록. "제거를 Definition of Done에 포함"
3. **오너 지정**: 누가 책임지고 제거할지 명확히
4. **월간/분기별 Flag 리뷰**: 팀 전체가 현재 살아있는 플래그 목록을 점검
5. **CI 통합**: 만료일이 지난 플래그가 있으면 빌드 경고 발생

### Q. 피처 플래그 구현 시 환경변수, DB, Redis, 외부 SaaS 중 어떤 걸 선택하나?

**핵심 키워드**: 동적 변경 여부, 타겟팅 필요성, 운영 비용

**모범 답변 방향**:  
요구사항에 따라 다르다.

**환경변수**: 동적 변경이 불필요하고 단순 on/off만 필요하면 충분. 단, 변경하려면 재배포 또는 재시작이 필요하다.

**DB**: 런타임에 변경이 필요하지만 소규모 서비스라면 간단한 DB 테이블로 구현 가능. 플래그가 많아지면 DB 부하 문제가 생기므로 로컬 캐시 레이어를 추가해야 한다.

**Redis**: 고성능이 필요한 분산 환경에서 적합. Pub/Sub으로 즉시 무효화가 가능하고 TTL 관리가 쉽다. 자체 구현 부담이 있다.

**외부 SaaS (LaunchDarkly, Unleash 등)**: 사용자 세그먼트별 타겟팅, A/B 테스트, 실시간 모니터링, 감사 로그 등 고급 기능이 필요할 때. 개발 비용은 낮지만 비용과 외부 의존성이 생긴다.

내가 직접 선택한다면: 초기에는 Redis + 자체 구현으로 시작해, 실험 기능이 중요해지면 GrowthBook(오픈소스)으로 전환하는 방식을 선호한다.

### Q. 피처 플래그와 Trunk-based Development의 관계를 설명하라.

**핵심 키워드**: 장기 브랜치 제거, 머지 충돌 감소, 지속적 통합

**모범 답변 방향**:  
Trunk-based Development는 모든 개발자가 main 브랜치(trunk)에 짧은 주기로 직접 커밋하는 방식이다. 문제는 아직 완성되지 않은 기능도 main에 올려야 한다는 점인데, 피처 플래그가 이 문제를 해결한다.

플래그 없이 장기 feature 브랜치를 유지하면:
- 수주~수개월 후 main과 머지할 때 충돌 위험
- 통합 테스트 지연
- "머지 지옥" 발생

피처 플래그로 미완성 코드를 비활성화한 채 매일 main에 머지하면:
- 항상 배포 가능한 상태 유지
- 머지 충돌 최소화
- CI/CD 파이프라인이 항상 최신 코드로 실행

단, 플래그로 비활성화된 코드도 테스트는 해야 한다. 플래그 ON 상태의 테스트를 별도로 작성하거나, CI에서 두 경로 모두 테스트하는 것이 중요하다.

## 실무 경험 연계 질문

### Q. 실제로 피처 플래그를 사용한 경험이 있나? 어떤 문제를 해결했나?

**모범 답변 방향 가이드**:

경험이 있다면: 구체적인 상황(어떤 기능, 왜 플래그가 필요했나), 구현 방식, 실제로 효과가 있었던 상황(롤백, 점진적 오픈 등)을 설명.

경험이 없다면: "직접 구현한 경험은 없지만, 개념적으로 이런 상황에서 사용했을 것"이라며 가상 시나리오를 구체적으로 설명. 예: "대용량 트래픽 서비스에서 새로운 결제 로직을 배포할 때, 장애 발생 시 즉시 롤백하기 위해 Ops 플래그로 감쌌을 것이다."

### Q. 피처 플래그 사용 시 테스트 전략은 어떻게 가져가나?

**핵심 키워드**: 플래그 ON/OFF 두 경로 모두 테스트, 플래그 조합 폭발 방지

**모범 답변 방향**:  
플래그가 있는 코드는 두 가지 경로(활성/비활성)를 모두 테스트해야 한다.

단위 테스트에서는 플래그 서비스를 Mock으로 교체해 각 경로를 독립적으로 테스트한다.

```go
// 플래그 ON 경로 테스트
mockFlag.On("IsEnabled", "new-payment", userID).Return(true)
result := handler.Handle(ctx, req)
assert.Equal(t, expectedNewFlow, result)

// 플래그 OFF 경로 테스트
mockFlag.On("IsEnabled", "new-payment", userID).Return(false)
result := handler.Handle(ctx, req)
assert.Equal(t, expectedLegacyFlow, result)
```

플래그가 많아지면 조합 수가 기하급수적으로 늘어나므로, **반드시 제거 계획과 함께 플래그를 추가**해야 테스트 복잡도가 통제 가능한 수준으로 유지된다.
