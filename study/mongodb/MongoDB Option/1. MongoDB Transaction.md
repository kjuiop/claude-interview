
## Write Concern

- 데이터가 잘 저장되었는지, 어디까지 확인해야하는지에 대한 설정
- 이 설정에 대한 데이터의 내구성, 데이터의 일관성의 차이를 다룰 예정
- 옵션
	- ACKNOWLEDGED
		- 프라이머리 노드가 쓰기 작업을 메모리에 적용 후 바로 응답
	- UNACKNOWLEDGED
		- 요청을 보내면, 저장 유무 상관 없이 성공을 응답
		- fire and forgot
	- MAJORITY
		- 세컨더리 노드까지 과반수의 합의가 된다면 응답 
	- W1, W2
		- 세컨더리 노드에서 성공을 합의하는 갯수가 충족된다면 응답
	- JOURNALED
		- 쓰기 작업이 디스크 저널에 기록이 된다면 응답


### Read Preference
- 읽기 우선순위 설정
- 레플리카 셋에서 설정, 읽기 작업이 어떤 노드에 라우팅 될지 설정하는 것
- Primary, Secondary, 기타 노드 중 어떤 노드에 커넥션이 진행이 되며, 읽기 쿼리가 동작하는지 설정하는 것
- 중요한 이유
	- 데이터 일관성 : 일관성의 중요성 여부, 얼마나 최신 데이터를 제공할 수 있어야 하는지 
	- 가용성 : 프라이머리가 장애가 발생해도 데이터를 읽을 수 있는 환경이 구축되어있는지
	- 성능 : mongodb 노드에 대한 부하  분산과 네트워크 지연을 해결할 수 있는지
	- 글로벌 서비스 환경 : 지역적으로 분산이 되어있고, 통신에 대한 거리가 멀어졌을 때 다른 사용자들에게 얼마큼 빠른 응답을 보내줄 수 있는지 (CDN 서비스)
- 옵션
	- PRIMARY
		- 데이터의 일관성을 보장하기 위한 가장 좋은 방법
		- 모든 읽기 요청은 반드시 PRIMARY 노드에 오도록 하는것
		- 항상 최신의 데이터, 데이터 일관성을 유지가능
		- 모든 쓰기 요청이 PRIMARY 에 오기 때문
		- 은행, 결제시스템, 이커머스와 같은 분야에서 사용됨
	- SECONDARY
		- 읽기 요청이 세컨더리 노드들 중에서 하나로 라우팅 되어 읽어온다.
		- PRIMARY 에서 복제한 데이터를 반환시킴
		- 읽기 복제몬의 노드에서 랜덤으로 선정해서 데이터를 제공함
		- 가용성이 높음, 일부 노드에서 장애가 있어도 계속해서 서비스 제공 가능
		- 복제본이기 때문에 Lag 가 발생할 시 최신 데이터를 제공하지 못할 수 있음
		- 대용량의 데이터를 읽어올 때 PRIMARY 노드에 부하를 주고 싶지 않을 때 사용됨
	- PRIMARY_PREFERRED
		- 기본적으로 PRIMARY 에서 읽어오지만, 장애 상황시에는 SECONDARY 에서 읽는다.
		- 네트워크 이슈 같은 상황에서도 대응 가능
		- 그러나 이것도 데이터 일관성이 떨어짐
		- 데이터 자체를 가져오고 조회하는게 분리되는 경우 운영 상황에서 디버깅도 어렵다.
	- SECONDARY_PREFERRED
		- 기본적으로 SECONDARY 에서 읽어오지만, 모두 장애시에는 PRIMARY 에서 데이터를 읽는다.
		- 최대한 PRIMARY 에 대한 부하를 줄이는 형태
		- 복제본을 통해 데이터를 읽어오기 때문에 데이터 일관성이 떨어짐
		- 대규모 통계성 데이터, 로그 분석과 같은 실시간성 중요도가 떨어질 때 사용됨
	- NEAREST
		- 가장 가까운 노드에 데이터를 읽어온다.
		- 네트워크 Latency 가 가장 낮은 노드의 데이터를 읽어오게 됨


### Spring 예시로 보는 MongoDB Lag 이슈

```java
@Service
public class RequestAddServiceImpl {

    @Autowired
    private MongoTemplate mongoTemplate;

    @Transactional("mongoTransactionManager")
    @Override
    public ResponseDto addRequest(RequestDto requestDto) {
        mongoTemplate.setWriteConcern(WriteConcern.ACKNOWLEDGED);
        mongoTemplate.save(requestDto.toEntity());
        // -> Primary 노드까지 진행이 된다면 응답을 받는다.
        // -> 세컨더리 노드에는 없을수도 있다.

        ReadPreference readPreference = ReadPreference.secondaryPreferred();
        // 복제본을 통해 데이터 조회
        // 기본적으로 secondary 를 바라보기 때문
        Document doc = mongoTemplate.getDb()
            .getCollection("request")
            .withReadPreference(readPreference)
            .find(new Document("_id", requestDto.getId()))
            .first();

        if (doc == null) {
            System.out.println("Lag 발생: Secondary에서 데이터 조회 실패");
        }

        return new ResponseDto(requestDto.getId());
    }
}
```
- 해결책 A) : Write Concern 을 MAJORITY 로 변경하면 모든 읽기 복제본에 복제가 끝나고 저장하기 때문에 데이터 일관성을 지킬 수 있음
- 해결책 B) : Read Concern 을 PRIMARY 로 변경하면 Primary 기준으로 가져오기 때문에 데이터 일관성을 지킬 수 있음
