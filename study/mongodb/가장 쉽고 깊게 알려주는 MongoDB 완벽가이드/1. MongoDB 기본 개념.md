
### NoSQL 의 등장 배경과 필요성

- CQRS (Command Query Responsibility Segregation) : 읽기와 쓰기를 분리하는 패턴
- Polyglot Persistence : 데이터 특성에 따라 DB 를 다르게 사용하자
- RDS : 스키마 변경이 어렵다, 데이터 확장이 어렵다, 복잡한 데이터를 표현하기 적합하지 않다


### NoSQL 의 다양향 유형과 MongoDB 만의 특징
- NoSQL : Not only SQL -> SQL 의 불편함을 해소하기 위해 만들어짐
- 키값 저장소 : Key - Value
- 문서 지향 데이터베이스 : 하나의 문서로 데이터가 저장됨
- 컬럼 기반 데이터베이스 : 열 중심으로 데이터가 저장됨
- 그래프 데이터베이스 : 데이터를 테이블이 아니라 노드와 관계로 저장하는 데이터베이스



### MongoDB 특징
- 개발자 친화적인
- 수평적인 확장 (레플리카 구조)
- 유연한 스키마 구조 (document 기반 저장)
- mongoDB 도 조인은 가능하나 성능이 잘 나오지 않아 지양하는 편임


### MonboDB vs MySQL 
- MySQL : 테이블 = MongoDB : 컬렉션
- MySQL 은 각 행마다 동일한 데이터 구조가 저장됨, mongoDB 는 document 마다 데이터 구조가 다름
- rdb 는 조인을 자주 활용되지만 mongodb 는 조인이 지양된다.
- mysql 은 컬럼 변경에 비용이 많이 들어가지만 Mongodb 는 컬럼 변경이 유연하게 가능하다.


### MonboDB vs MySQL 쿼리 비교

```sql

INSERT INTO users (id, name, department) VALUES (1001, '김철수', '컴퓨터') 
db.users.insertOne({ id : 1001, name : "김철수", department : "컴퓨터", }) 

------ 

SELECT * FROM users WHERE depatment = "컴퓨터" 
db.users.find({deparment : "컴퓨터"}) 

----- 
UPDATE users SET department = 'TEST' WHERE id = 1001 
db.users.updateOne({id : 1001}, {$set : {deparment : "TEST"}}) 
------ 

SELECT s.name, g.course FROM users AS s 
JOIN grades ON s.id = grades.users_id WHERE s.name = '김철수' 
db.users.find({name : "김철수"}, {name : 1, grades.course : 1})

```



### MongoDB 의 주요 특징과 장점들

- mongodb 는 문서 모델을 따른다.
	- 객체 자체를 문서에 저장이 가능하기 때문에 객체 지향 프로그래밍과 호환이 좋다.


```javascript
const user = {
	 name : "개발", 
	 age : 123, 
	 skilss : ["js", "java"], 
	 address : { city : "서울" ... } 
} 

db.users.insertOne(user) 
db.users.insertOne({name : "김철수"}) 
db.users.insertOne({name : "김철수", 마음대로 넣어야지 : "마음대로"})

```

- 단일 컬렉션에 대한 조회 자체가 매우 빠르다
- 인덱스, 복합 인덱스 등 성능에 대한 지원이 좋다.
- mongodb 는 내부적으로 메모리 매핑 파일이 존재하여 디스크 I/O 를 효과적으로 관리한다.
- 샤딩도 지원한다.
	- 샤딩이란 샤딩 키를 잡고 그 키를 기반으로 데이터를 분산 저장하는 것을 의미한다.
- 레플리카 Set 이 존재한다. 데이터 복제가 가능하다.


### MongoDB 의 샤딩, 메모리 매핑파일, 레플리카 셋 이해하기

- 샤딩 : 분할, 대용량의 데이터를 여러 노드로 분산해서 저장하는 기법
	- 샤드 : 데이터를 저장하는 서버
	- 컨트롤러 : mongos, queryRouter, 클라이언트의 요청을 해당하는 샤드 서버로 전달
	- 구성 서버 : 샤드 서버 정보 및 메타데이터를 관리
	- 샤딩 키 : 인덱스, 데이터를 분산시킬 때 기준이 되는 키 (userId, orderNo), 데이터 불균형을 잘 잡아야 함 ,따라서 고유한 값을 기준으로 샤딩키를 사용하는 경우가 있음
	- 장점 : 수평적 확장이 가능
	- 단점 : 샤딩키가 기준이기 때문에 부하가 특정 서버로 몰릴 수 있음
		- 서버를 여러 대 사용하기 때문에 복잡성이 증가할 수 있음
	- 단일 서버 : 대용량의 트래픽이 있을 때 단일 서버로 트래픽이 몰릴 수 있기 때문에 분산이 필요

```
Clinet -> Mongos(라우터) -> Shard1|Shard2|Shard3 
              | 
          Config Server 

userId 1 ~ 1000 -> Shard1 
userId 1001 ~ 2000 : Shard2 
userId 2001 ~ 3000 : Shard3
```

- 메모리 매핑 파일
	- 운영체제의 가상 메모리를 활용, 파일 내용을 메모리 주소공간에 매핑해서 파일처럼 접근함
	- 디스크에 접근해서 가져오는 데이터 접근 방법은 느리기 때문에 메모리 매핑 파일로 데이터 가져오는 것이 성능 상 좋음

- 레플리카 셋
	- 동일한 데이터를 여러 서버에 복제해놓고 사용하는 것
	- Primary Node 장애가 발생하면 Secondary Node 가 대체해서 Primary 로 승격됨
	- 홀수개의 노드가 기본 구성 (3개)
	- 읽기 트래픽을 분산시킬 수 있음 -> Primary 부하를 줄일 수 있음
	- 그러나 데이터 복제에 대한 Lag 가 발생할 수 있어 데이터 불균형이 발생할 수 있음
	- 장점 : 데이터 고가용성, 부하에 대한 분산이 가능
	- 단점 : 서버 수 만큼의 비용, 데이터 복제에 대한 지연이 발생할 수 있음, 데이터 불균형 가능성 있음
