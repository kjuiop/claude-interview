오늘의 면접 질문 10개를 준비한다. 반드시 아래 순서대로 실행한다.

## 인자 처리

스킬 호출 시 회사명 인자가 있는지 확인한다.

- **인자 있음** (예: `/출근 화이트큐브, 넵튠`): 명시된 회사들의 `job.md`만 참조한다.
  - 회사명으로 `jobs/` 하위 폴더를 매핑한다 (예: 화이트큐브 → `whitecube-challengers`, 넵튠 → `neptune-backend`)
  - `_archive/` 하위는 제외한다
- **인자 없음**: `jobs/` 하위의 모든 활성 `job.md`를 참조한다 (`_archive/` 제외)

## Step 1 — 소스 문서 파악 (병렬 실행)

다음 파일들을 동시에 읽는다:
- `resume/profile.md` — 지원자 기술 스택과 경험
- 대상 회사의 `job.md` — 공고 요구사항 및 기술 스택 (인자 처리 결과 기준)
- `topics/` 하위의 모든 `questions.md` — 현재 정리된 면접 질문 풀

## Step 2 — 출제 이력 확인

`daily/` 폴더의 모든 파일을 읽어 최근 출제된 질문 목록과 답변 품질을 파악한다.

### 잘 맞춘 질문 추적 (항상 적용)

daily/ 파일의 세션 기록에서 피드백을 분석해 아래 기준으로 분류한다:

- **잘 맞춘 질문**: 점수 6/10 이상이거나, 피드백의 "보완 필요" 항목이 핵심 개념이 아닌 세부 수준(내부 구현, 수치 암기, 학술적 분류 등)인 경우
- **재출제 필요 질문**: 점수 5/10 이하이거나, "모르겠습니다"로 답한 경우, 또는 핵심 개념(동작 원리·선택 기준·트레이드오프)이 완전히 빠진 경우

> **재출제 시 질문 원문 보존 규칙 (반드시 준수)**
> 재출제 필요 질문으로 분류된 경우, 해당 질문을 daily/ 파일에서 찾아 **문자 그대로 복사**한다.
> 단어 하나, 조사 하나도 변경하지 않는다. 새로운 각도나 추가 조건을 붙이는 것도 금지한다.
> 이미 틀린 질문을 다시 풀어야 하는데 질문이 바뀌면 사용자는 무엇이 달라진지 파악하는 데 에너지를 쓰게 된다.

> **보완 필요 항목 필터**: 피드백의 보완 사항 중 "한국 백엔드 면접에서 실제로 검증될 가능성이 낮은 세부 사항"은 재출제 판단에서 제외한다. 예: 내부 자료구조 구현, 라이브러리 세부 수치, 알고리즘 세부 단계 등.

**가중치 규칙:**
- 같은 질문(또는 실질적으로 동일한 내용)을 **2회 이상 잘 맞춘 경우** → 오늘 출제 목록에서 제외하고, 동일 토픽의 다른 각도 질문으로 대체한다
- 잘 맞춘 질문이 많은 토픽은 같은 토픽 내 아직 다루지 않은 심화 질문으로 교체한다
- 재출제 필요 질문은 가중치를 높여 오늘 목록에 포함시킨다

**회사명 인자가 없는 경우 (일반 모드):**
- 최근 7일 이내 출제된 질문은 제외한다 (단, 재출제 필요 질문은 예외)
- 같은 주제가 3일 연속 나오지 않도록 한다
- 아직 한 번도 다루지 않은 topics 폴더가 있으면 우선 출제한다

**회사명 인자가 있는 경우 (회사 타겟 모드):**
- 중복/연속 제한을 적용하지 않는다
- 대신 "해당 회사 면접에서 나올 확률이 높은가"를 최우선 기준으로 삼는다
- 이전에 잘 맞춘 질문이라도 공고 핵심 기술이면 더 심화된 각도로 재출제할 수 있다
- 출제 이력은 "같은 질문을 그대로 반복하지 않기" 정도의 참고용으로만 활용한다

## Step 3 — 웹 검색으로 최신 트렌드 보강

WebSearch로 다음을 검색한다:
- `백엔드 개발자 면접 최신 트렌드 {현재연도}`
- 대상 공고에 있는 기술 중 최근 이슈나 변경사항

## Step 4 — 오늘의 질문 10개 선정

**구성 비율: 기초 7개 + 중급 3개**

> 인자로 회사명이 지정된 경우, 해당 공고의 기술 스택과 우대 사항을 우선 반영한다.
> 복수 회사가 지정된 경우, 공통 기술은 가중치를 높이고 회사별 특이 스택은 1~2개씩 포함한다.

### 회사 기술 스택 필터 (인자로 회사명이 지정된 경우 반드시 적용)

**질문 pool을 회사 스택으로 제한한다.**

- `job.md`에서 기술 스택을 파악한 뒤, 해당 스택에 **없는** 언어·프레임워크 관련 질문은 출제하지 않는다.
  - 예: 공고에 Go, Python만 있으면 → Java, Spring, Kotlin 질문 제외
  - 예: 공고에 MySQL, Redis만 있으면 → PostgreSQL, Cassandra 질문 제외
- 공고 기술 스택이 명시되지 않은 경우(예: 추정 스택), 이력서(`resume/profile.md`)의 기술 스택을 기준으로 한다.
- 단, **범용 백엔드 지식**(네트워킹, 분산 시스템, 시스템 설계)은 스택 제한 없이 출제 가능하다.

### 이력서 연계 필터 (항상 적용)

`resume/profile.md`를 읽고 아래를 반영한다:

- **이력서에 있는 기술**: "실무에서 사용했다고 했는데 실제로 아는가" 관점으로 질문 구성
- **이력서 대표 성과와 연결**: 질문 본문에 "이력서의 XX 경험과 연결해서 설명해주세요" 형태로 연결 가능하면 연결
- **이력서에 없는 기술**: 공고 요구사항이면 "경험은 없지만 개념 수준으로 설명 가능한가" 관점으로 출제

### 질문 현실성 필터 (선정 전 반드시 확인)

아래 기준으로 탈락시킨다:
- **탈락**: 런타임/컴파일러 내부 구현 수준 (예: Write Barrier 종류, GC 알고리즘 세부 단계, 어셈블리 레벨)
- **탈락**: 한국 백엔드 개발자 면접에서 실제로 출제될 가능성이 낮은 학술적 질문
- **통과**: "이 기술을 실무에서 어떻게 써봤나", "이 상황에서 어떤 선택을 하겠나" 수준
- **통과**: 개념 정의, 동작 원리(블랙박스 수준), 트레이드오프, 실무 패턴, 장애 대응

> 기준: "일반적인 한국 백엔드 스타트업/중견기업 면접관이 실제로 물어볼 법한가?"

### 기초 7개 선정 기준
1. **주제 다양성 필수**: 7개가 서로 다른 topic에서 출제되도록 한다 (같은 기술 폴더에서 2개 이상 금지)
2. **개념 검증**: "이 기술을 쓴다고 했는데 기본 개념은 아는가" 수준의 질문
3. **이력서 연계**: 지원자가 실무에서 사용한 기술 우선 — 경험 없어도 개념 수준으로 대답 가능해야 함
4. **공고 필수 스택 커버**: 대상 공고의 기술 중 아직 기초도 안 다룬 것 우선

### 중급 3개 선정 기준
1. **이전 세션 피드백 반영**: daily/ 기록에서 "다음에 집중할 주제"로 명시된 것 우선
2. **꼬리 질문에서 막힌 주제**: 이전 세션에서 "모르겠습니다"로 답한 항목 재출제
3. **공고 우대 역량**: 대상 공고에서 우대하는 기술

각 질문은 다음 형식으로 구성한다:
- 질문 본문
- 관련 topic: `[[topics/{기술}/questions]]`
- 난이도: 기초 / 중급
- 출제 의도: 왜 이 질문을 오늘 선택했는지 한 줄
- 대상 회사: (인자로 회사가 지정된 경우) 어느 공고 기준인지 표시
